# 需求说明补充章节：自动归拢与来源可信度（第 16 节）

> 本文件作为《IP-Passport-开发需求说明.md》的补充章节，供更新需求文档时使用。
> 编写依据：当前实现的代码事实（2026-11-21 17:38 核查），以及第 15 节法律表述约束。
> **本文件描述的是路线图，不代表已实现功能。** 提交材料中的功能宣称须与当前 demo 一致。

## 16.1 设计原则（优先级高于「怎么归拢」）

1. **证据必须在创作当时记录。** 链上锚定的时间是**区块时间戳**（由出块方决定），不是用户机器时钟。纠纷发生后再补录，链上时间即为纠纷之后，无法支持「作品当时就存在」的主张。
2. 因此归拢必须尽量**自动、随手、低摩擦**；任何需要用户事后手动整理的路径都会削弱证明力。
3. **本地优先**：原文件、盐、Prompt 内容不上传任何服务器；只有指纹与 Merkle 根上链。
4. **时间语义要区分**：`createdAtLocal` 是用户机器上的自述时间，可被修改，**不是可信时间戳**；可信时间只有链上 `blockTimestamp`。UI 与证据包须明确标注两者区别，避免被误读。

> 这一条是对第 15 节的延伸：即便只说「最晚在对应区块时间已存在」，也不得让「本地记录时间」看起来像可信时间来源。

## 16.2 与当前实现的差距（分两层）

### A 层：需求文档已规定、但当前实现为赶提交省略的功能

| 需求条目 | 规定内容 | 当前状态 |
|---|---|---|
| 8.1 `ipp snapshot --git` | 以 HEAD 为 COMMIT 版本，纳入 `git ls-files`，记录 commit 哈希 | ❌ 未实现 |
| 8.1 `ipp hook install` | 安装 git `post-commit` 钩子，提交即自动入队 | ❌ 未实现 |
| 8.1 `ipp flush` | 队列按 5.4 打批次，一次 `anchorBatch` | ❌ 未实现（`--queue` 可入队但无 flush） |
| 5.5 / 8.2 `meta.tool` | 可选，所用 AI 工具名称 | ⚠️ schema 已建、值未填、UI 未显示 |
| 5.5 `meta.gitCommit` | 可选，git commit 哈希 | ⚠️ schema 已建、值未填 |

> **重要**：`MetaSchema` 中 `tool` / `gitCommit` 是需求文档 5.5 明文规定的字段，zod 为非 strict 对象。把它们填值、显示、写进证据包，**不需要改变第 5 节哈希格式**，不影响已上链演示数据。

### B 层：需求文档未覆盖、需新增的能力

| 目标 | 现状 | 缺口性质 |
|---|---|---|
| 文件夹监听（保存即生成版本） | 无 `watch` / `chokidar` 依赖 | 新增 CLI 常驻进程 + 防抖 + 去重 |
| 每条记录标注来源平台 | 仅有 `kind`（PROMPT/DRAFT/COMMIT/RELEASE） | 填 `meta.tool` + 新增来源枚举（零格式风险） |
| 时间线按来源显示 | 前端只显示 `kind` + `createdAtLocal` | 前端模板增一行（零格式风险） |
| 平台侧可核对标识写入证据包 | `chain.json` 只有 versionRoot/kind/时间/tx | 新增可选字段，不参与哈希 |
| 浏览器插件 | 无 | 全新组件（Chrome MV3） |
| zkTLS 来源证明 | 无 | 研究级，需第三方协议集成 |

### 现状一句话
当前只有**手动** `ipp snapshot <file> --kind ...`，无 git 钩子、无文件夹监听、无浏览器插件、无来源标识。归拢与「创作当时记录」目前依赖用户主动执行一条命令，与 16.1 的原则存在明显差距。

## 16.3 各平台归拢方案（沿用讨论稿，标注实现依赖）

| 来源 | 归拢方式 | 自动化 | 依赖 |
|---|---|---|---|
| GitHub / 本地代码 | git `post-commit` 钩子 → `snapshot --git --queue` → `flush` | 全自动 | A 层补齐即可 |
| Cursor / Claude Code | 代码由 git 钩子覆盖；本地对话文件由文件夹监听 | 全自动 | A 层 + 文件夹监听 |
| 本地设计稿 / 文档 | 监听指定作品文件夹，保存时生成新版本 | 全自动 | 新增 watcher（防抖、去重、忽略临时文件） |
| 网页版 AI 对话 | 浏览器插件「记录本轮对话」，本地保存页面内容并计算指纹 | 一键 | 新增插件 |
| AI 生图 | 插件记录 Prompt、参数、任务编号与图片 | 一键 | 新增插件 |
| Figma 等在线设计 | 官方接口导出版本历史 | 半自动 | 后续 |
| 平台官方数据导出 | 拖入补录 | 手动 | `ipp snapshot` 已支持 |
| 社媒发布记录 | 记录链接与截图，可同时提交 Internet Archive 快照 | 一键 | 新增；快照属第三方服务，须审查条款 |

**归拢结果**：本地作品档案按时间排成单一时间线，每条带来源标签与链上状态；所有内容留在本机，可选加密备份到用户自有 OneDrive / iCloud。

## 16.4 争议时的证据包（已实现，无需新增）

1. 选择作品与版本 → 2. 工具自动带出从第一条到该版本的整条 `prevVersionRoot` 路径 → 3. 逐项勾选披露（未披露项只保留 `leaf`，路径可 redact）→ 4. 导出 zip，对方在 `/verify` 拖入即可离线 + 链上双重核对。

已实测：`export --disclose` → `verify` 闭环通过；篡改包被正确识破。

## 16.5 来源可信度分级与法律定性

**核心限制（讨论稿判断正确）**：从网页保存的对话，链上只能支持「这份内容最晚在该区块时间已存在」，**不能支持「这段对话真的发生在 ChatGPT 上」**——内容可自行编造后再上链。

| 强度 | 办法 | 第三方可核对什么 | 法律定性 |
|---|---|---|---|
| 中 | 平台侧标识（分享链接、commit 哈希、任务编号） | 拿标识回平台核对 | 仍是间接佐证，依赖平台配合 |
| 中高 | 平台发出的签名邮件（DKIM） | 验证邮件确由该域名发出 | 电子证据材料之一 |
| 高 | zkTLS（TLSNotary / Reclaim） | 密码学证明内容来自特定域名，无需平台配合 | 仍需争议处理机构依法域规则审查 |

**补充两点（法务视角）**：
- 即便 zkTLS 成立，也只把证明力推进到「内容来自该域名」，**仍不等于证明作者身份或版权归属**；第 15 节的表述上限不变。
- 浏览器插件仅在本人的页面、由本人点击后保存，且只存本地，隐私与平台条款风险相对可控；但**上线前须逐一核对各平台用户协议**，且社媒快照涉及第三方服务，需单独审查。

**zkTLS 作为黑客松创新亮点**是成立的（对应「新颖机制」），但实现难度高。建议仅对一个来源（如 ChatGPT 分享页）做概念演示，其余列入路线图；且必须标注为「概念演示」，不得宣称已具备完整来源证明能力。

## 16.6 优先级与提交口径

| 优先级 | 内容 | 是否改动第 5 节数据格式 |
|---|---|---|
| **P0-A** | 填 `meta.tool`（`--source` 参数）；前端时间线与 `chain.json` 显示来源；证据包写入平台侧标识 | 否（5.5 已预留） |
| **P0-B** | 文件夹监听；`snapshot --git`；`hook install`；`flush` | 否 |
| **P1** | 浏览器插件（ChatGPT + Midjourney 两站） | 否 |
| **P2** | zkTLS 概念演示（单一来源） | 否 |

### 提交口径建议（重要）
- 提交材料**只宣称已实现的功能**：手动快照、链式锚定、证据包自动打包与验证、时间点许可查询、下游市场检查。
- 「自动归拢 / 来源标注 / 浏览器插件 / zkTLS」一律写成 **Roadmap / 规划中**，并附本补充章节作为设计完整性的证明。
- 黑客松评审会对照 demo 核验；把规划写成已实现，风险远大于少写一个亮点。
- 若时间允许，优先做 **P0-A**：零数据格式风险、可当场演示「来源标签时间线」，且能直接回应「归拢」这个原始诉求，性价比最高。

## 16.7 与第 15 节的关系

本补充章节所有新增 UI 文案继续受第 15 节约束：
- 时间线可写「来源：ChatGPT 分享页」「最晚于该区块时间已存在」，不得写「已验证归属」「证明作者身份」「证明拥有版权」。
- 来源标签只是**作者自述的元数据**，须在证据包 README 中明确「来源标签由记录方填写，未经独立验证」。
- 义务提示仍只给义务列表与风险等级，不写「可以商用 / 不能商用」。
