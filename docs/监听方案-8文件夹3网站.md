# 监听方案：8 个本地文件夹 + 3 个网站

> 对应《需求补充-自动归拢与来源证明》第 16 节 P0-B。
> **本文件是设计与配置规格，当前代码尚未实现 watcher**。提交材料中请按「路线图」表述。

---

## 一、先分清两类对象

| 对象 | 能不能「监听」 | 原因 | 机制 |
|---|---|---|---|
| 本机 8 个文件夹 | ✅ 能 | 文件在自己磁盘上，OS 会发出文件系统事件 | 1 个常驻 watcher + 8 条路径配置 |
| 3 个网站 | ❌ 不能 | 内容在别人服务器上，本机没有事件可听 | 只能「取回」：git 钩子 / 浏览器插件 / 官方导出 |

**不要为 8 个文件夹起 8 个进程**，也不要试图让程序去「盯着」网页——网页侧必须有一个动作把内容带到本机（点击插件、导出文件、git commit），之后才进入同一条流水线。

## 二、8 个文件夹：一个 watcher，八条规则

配置文件 `.ipp/watch.config.json`（示例，路径按实际替换）：

```json
{
  "debounceMs": 3000,
  "queueThreshold": 10,
  "flushIntervalMin": 30,
  "ignore": [
    "**/.git/**", "**/node_modules/**", "**/.DS_Store",
    "**/~$*", "**/*.tmp", "**/*.swp", "**/*.part", "**/.ipp/**"
  ],
  "roots": [
    { "path": "~/Projects/ip-passport/src",        "workId": "auto", "kind": "COMMIT",  "source": "local-git",   "ref": "git" },
    { "path": "~/Projects/ip-passport/docs",       "workId": "auto", "kind": "DRAFT",   "source": "local-doc" },
    { "path": "~/Design/夏日海边",                  "workId": "auto", "kind": "DRAFT",   "source": "Photoshop" },
    { "path": "~/Writing/公众号长文",               "workId": "auto", "kind": "DRAFT",   "source": "local-doc" },
    { "path": "~/Downloads/ChatGPT-导出",           "workId": "auto", "kind": "PROMPT",  "source": "ChatGPT",    "ref": "official-export" },
    { "path": "~/Downloads/Midjourney",             "workId": "auto", "kind": "DRAFT",   "source": "Midjourney" },
    { "path": "~/Legal/合同与审查意见",             "workId": "auto", "kind": "DRAFT",   "source": "local-doc" },
    { "path": "~/Archive/发布截图与链接",           "workId": "auto", "kind": "RELEASE", "source": "小红书" }
  ]
}
```

**`workId` 的两种用法（需要您定，影响架构，我不替您假设）**：
- 8 个文件夹属于**同一个作品** → 全部填同一个 workId，归到一条时间线（上面示例用 `auto` 表示取当前目录 `.ipp/config.json`）
- 8 个文件夹是**8 个不同作品** → 每条各填自己的 workId，watcher 按路径分流到不同作品档案

### 事件处理流水线

```
文件落盘
  → 忽略规则过滤（临时文件、.git、自动保存副本）
  → 防抖 3 秒（Word / PS / VS Code 保存会连写多次）
  → 计算 fileDigest，与该文件上一次快照比对；相同则跳过（内容去重）
  → ipp snapshot <file> --kind <规则> --source <配置> --ref <配置> --queue
  → 队列累积到 10 条或满 30 分钟 → ipp flush（一次 anchorBatch 上链）
```

**为什么入队而不是逐条上链**：8 个文件夹 + 自动保存会产生高频事件，逐条上链既费 gas 又制造大量无意义版本；批量锚定（需求 5.4）把多个 versionRoot 打成一棵树，一次交易落链，证据包里带各自在批次树中的 Merkle 证明。

### 三个必须处理的坑

1. **临时文件**：Word 的 `~$xxx.docx`、PS 的临时层、VS Code 的 `.swp`，不忽略会产生海量垃圾版本
2. **内容去重**：编辑器自动保存但内容没变时，不应生成新版本（比对 `fileDigest` 而非 mtime）
3. **开机自启**：watcher 必须常驻才有意义（macOS 用 launchd plist；`ipp watch start` 后台运行 + 日志）。**没开电脑的时间段没有覆盖**——见第五节

## 三、3 个网站：按类型选通道

把您实际的 3 个网站按下面的特征对号入座：

| 网站特征 | 通道 | 自动化 | 落地形态 |
|---|---|---|---|
| 有 git 仓库（GitHub / 内部 GitLab） | `post-commit` 钩子 → `ipp snapshot --git --queue` | 全自动 | `ipp hook install` 生成 `.git/hooks/post-commit`；记录 commit 哈希到 `meta.gitCommit` |
| 网页 AI 对话（ChatGPT / Claude / 豆包 / Kimi） | 浏览器插件，点「记录本轮对话」 | 一键 | MV3 插件读取当前页 DOM，本地保存为文件 → `ipp snapshot --source ChatGPT --ref <分享链接>` |
| 在线设计 / 文档（Figma / 在线文档） | 官方 API 导出版本历史，或定时导出 | 半自动 | 导出文件落到被监听的文件夹，自动进入第二节流水线 |
| 无 API、无插件可用 | 平台「导出数据」功能，拖入补录 | 手动 | 已有 `ipp snapshot` 支持，作为兜底 |

> 插件只在**用户本人的页面、由用户点击后**保存内容，且只存本地，隐私与平台条款风险相对可控；上线前仍需逐一核对各平台用户协议。

三条通道产出的都是同一条命令 `ipp snapshot --source ... --ref ...`，因此和 8 个文件夹自然汇成**一条按时间排序、带来源标签的时间线**——这就是「归拢」。

## 五、法律上的边界（第 15 节 / 16.1）

- watcher 只能证明「**文件落盘那一刻**」的指纹最晚在对应区块时间存在，**不能证明「创作当时」**。如果创作发生在网页上、几天后才导出到本机，链上时间是导出时刻，不是创作时刻。
- 所以 16.1 的原则仍然成立：网页侧必须在**对话当下**由插件记录，把时间窗压到最小；事后的官方导出只能作为补充材料。
- 来源标签是**记录方自述的元数据，未经独立验证**；`--ref` 里的分享链接 / commit 哈希 / 任务编号只是供第三方回平台核对的线索，不等于来源已被证明。
- 链上可信时间是**区块时间戳**；`createdAtLocal` 是本机自述时间，未经独立验证（前端已按 16.1 标注）。
