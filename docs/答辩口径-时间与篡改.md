# 答辩口径：监听原理、上链时间、篡改边界

> 供 MOJO 评审问答及后续法务沟通使用。所有措辞遵守需求文档第 15 节。
> 核心结论前置：**系统保证「内容↔指纹的绑定在上链后不可篡改」，不保证「链上时间等于创作完成时间」。**

---

## Q1 监听本地文件夹的原理是什么？

**不是程序去"看"文件，是操作系统在文件变化时主动通知。**

1. 应用向 OS 注册监听路径（macOS `FSEvents` / Linux `inotify` / Windows `ReadDirectoryChangesW`，Node 侧通常用 `chokidar` 封装）
2. 文件被写入、重命名、删除时，内核发出事件，watcher 收到路径
3. **防抖**：编辑器保存常伴随多次写入（临时文件 → 原子替换 → 写元数据），等 3 秒静默才认定"这一次保存结束"
4. 读取文件**字节** → SHA-256 → 加盐叶子 → Merkle `fileRoot` → `versionRoot`
5. 发交易把 `versionRoot` 写入合约

**一个容易误解的点**：文件系统事件的含义是「**这一版字节被写到了磁盘**」，不是「**作品完成了**」。PS 保存 20 次就有 20 个版本，系统锚定的是每一次保存的字节序列；"完成"是作者事后在时间线上的指认，属于自述，不是密码学事实。

---

## Q2 上链的时间是什么？

**系统里有两个时间，只有一个可信。**

| 时间 | 来源 | 性质 |
|---|---|---|
| `createdAtLocal` | 本机时钟，写进 manifest | **自述时间，可修改，不是可信时间戳**；前端已明确标注 |
| `blockTimestamp` / `blockNumber` | 出块方在区块里写入，合约用 `block.timestamp` 读取 | 链上可信时间；受共识规则约束 |

**合约事实（已核代码）**：`anchorVersion(bytes32 workId, bytes32 versionRoot, bytes32 prevRoot, VersionKind kind)` 的函数签名里**没有任何时间参数**。`timestamp` 由 `uint64(block.timestamp)` 在合约内部取值，调用者无法传入或指定一个假时间；`setLicense` 的 `effectiveFrom` 同理。所以"自己写一个 3 月的时间上链"在本系统里做不到。

**但**：从文件落盘到出块之间仍有时间窗（防抖 3 秒 + 哈希计算 + 交易广播 + 出块；若入队等 `flush`，可达 30 分钟）。链上时间 T 是**记录动作完成的时刻**，不是**创作发生的时刻**。

**准确表述（第 15 节）**：链上记录只能证明「**某一版本的指纹最晚在对应区块时间已经存在**」。这是一个**上界（不晚于 T）**，不是「创建于 T」，更不是「完成于 T」。哈希锚定给不出下界。

---

## Q3 为什么能保证上链的是完成的时间，而不是被篡改了？

**必须分三层回答，混在一起就会过度承诺。**

### 第一层：上链之后改内容 —— 能保证发现 ✅

链上存的是 `versionRoot`，不是文件、不是文件名、也不是一个时间标签。它由 `文件内容哈希 + workId + prevVersionRoot + metaHash` 共同决定：

- 改文件任意一个字节 → `fileDigest` 变 → 叶子变 → `fileRoot` 变 → `versionRoot` 变 → 与链上值不符，验证立即失败
- `prevVersionRoot` 把版本串成链：改动中间任何一版，后面所有版本的链式关系全部断裂
- 验证方在浏览器本地重算，不需要信任任何服务器

这是**密码学保证**，也是产品真正兑现的部分（已实测：篡改证据包被正确识破）。

### 第二层：链上记录本身被改 —— 不能由用户单方面做到 ✅

`versionRoot → (workId, prevRoot, timestamp, blockNumber, kind)` 由合约写入，受链上共识与 `owner` 权限约束；时间由 EVM 提供，调用者无法传参伪造。要改需推翻该链的共识，不是改本机文件能做到的。

### 第三层：上链之前篡改 / 事后编造 —— **不能保证** ❌（这是关键）

如果有人在纠纷发生后编一段对话、改一版文件，再跑一次 `snapshot` 上链，那么：

- 哈希自洽 ✅、链上记录合法 ✅、时间真实 ✅
- 但链上时间就是**纠纷之后**，系统**无法区分**「3 月创作的」和「11 月编的 3 月」

**链上时间戳可信 ≠ 内容创作时间可信。** 系统能证明的始终是「这份内容不晚于 T 存在」，永远无法证明「这份内容产生于 T 之前」。同理，来源标签（ChatGPT / Midjourney）只是记录方自述的元数据，未经独立验证；链上也不证明作者身份或版权归属（第 15 节）。

### 那"尽量接近创作当时"靠什么？

不是靠密码学，是靠**把时间窗压到最小 + 引入独立时间锚**：

1. 自动化（文件夹监听 / git 钩子 / 浏览器插件）在创作当下就记录，减少"事后补录"的空档
2. 平台侧可核对标识（分享链接、commit 哈希、任务编号）供第三方回查
3. 平台发出的 DKIM 签名邮件、或 zkTLS 来源证明，提供独立于本机的第三方时间/来源线索
4. 多源交叉印证（对话 → 草稿 → 定稿 → 发布记录形成连续时间线）

这些都属于「可作为电子证据材料之一，由争议处理机构依据所在法域规则审查」，**没有单一技术能自证创作时间**。

---

## 一句话标准答复

> 我们不宣称链上时间就是作品完成时间。链上存的是内容指纹与版本链，时间由区块提供、调用方无法伪造，因此能证明「这一版内容最晚在该区块时间已存在，且此后任何改动都会被验证发现」；至于内容是否创作于更早、是否来自所声称的平台、谁是作者，链上不作证明，需结合平台标识、签名邮件等多源材料由争议处理机构依法域规则审查。

## 评审可能追问

| 追问 | 应答要点 |
|---|---|
| 「能不能自己填一个假时间上链？」 | 不能。合约用 `block.timestamp` 取时间，函数签名无时间参数；`createdAtLocal` 是本机自述时间，UI 已标注不可信 |
| 「那这个时间戳有什么用？」 | 给的是上界（不晚于 T）。争议中可用于排除「T 之后才出现」的主张，但不能单独证明创作时点 |
| 「能证明是原创的吗？」 | 不能。不证明作者身份、不证明拥有版权、不意味着链上登记即获得版权保护 |
| 「和公证有什么区别？」 | 不是公证，不具法定公证效力；只是技术性哈希与链上记录，可作为电子证据材料之一 |
| 「怎么防止我事后编一段对话？」 | 单靠本系统防不住；靠创作当下的自动记录压缩空档，加平台侧标识 / DKIM 邮件 / zkTLS 交叉印证 |
